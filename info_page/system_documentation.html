Hybrid Parcel Tracker - System Documentation

1. Introduction

The Hybrid Parcel Tracker is a high-performance system designed for simulating the trajectories of air parcels within atmospheric or oceanic flows. It leverages a hybrid C++/Python architecture to combine the computational efficiency of C++ for core calculations with the flexibility and ease of use of Python for orchestration, data handling, and visualization.

Authors: Manish Shukla (Postdoctoral student, Indian Institute of Technology Hyderabad, manishshukla01@live.com) and R. Maheshwaran (Assistant Professor, Indian Institute of Technology, Hyderabad)

This document outlines the system's architecture, data processing flow, core algorithms, mathematical formulas, and key implementation details.

2. System Architecture

The system is composed of several key components that interact to perform the simulation:

  • Python Orchestrator (particle_tracker.py): The main driver of the simulation. It handles configuration, manages the simulation loop, calls data loading routines, invokes the particle update engine, and coordinates output and visualization.
  • C++ Particle Engine (particle_engine_cpp module): A compiled C++ extension (using Pybind11) that performs computationally intensive tasks. It includes:
    • ParticleEngine: Main C++ class callable from Python.
    • RK4Integrator: Implements serial Runge-Kutta 4th order integration.
    • RK4IntegratorParallel: Coordinates multi-threaded RK4 integration using OpenMP.
    • RegularGrid3DInterpolator: Performs fast 3D trilinear interpolation of velocity fields.
    • ThermoState: Implements thermodynamic tracking and Papritz & Röthlisberger decomposition integrations.
  • Data Handlers:
    • CSV Data Loader (data_loader.py - VelocityDataLoader class): Loads velocity components from individual CSV grids.
    • NetCDF Data Loader (nc_data_loader.py - NCDataLoader class): Handles scanning and loading of multi-variable NetCDF dataset files (e.g., HRRR/ERA5 files).
    • API Data Handler (api_data_handler.py - APIDataHandler class): Manages downloading and processing of meteorological data from Copernicus CDS API.
    • Climatology Background Downloader (data_downloader_method2.py): Companion downloader utility that queries historical baseline windows from CDS API to compute mean temperature fields ($\overline{T}$) and their gradients.
  • Visualization (visualization.py - ParticleVisualizer class): Generates plots of particle positions, trajectories, and other diagnostic information using Matplotlib and Cartopy.
  • Configuration (run_simulation.py): A Python script where users define all simulation parameters, input/output paths, and model settings.

4. Data Handling

The system supports two primary data sources: pre-processed CSV files and direct downloads via an API (e.g., ERA5 from CDS).

4.1. CSV Data (VelocityDataLoader)

When data_source is "CSV", the VelocityDataLoader class is used.

  • File Structure: Expects CSV files organized into subdirectories for each variable (e.g., u/, v/, w/). Filenames typically follow a pattern like {variable}_{pressure_level}_{hour_index}.csv (e.g., u_500_1.csv). Each CSV file contains 'Latitude', 'Longitude', and the variable's value for that specific pressure level and time index.
  • Loading Process:
    1. For a given variable (u, v, or w) and hour_index, it iterates through all configured pressure_levels.
    2. Reads the corresponding CSV file for each pressure level.
    3. Concatenates data from all pressure levels into a single Pandas DataFrame.
    4. Constructs a 3D NumPy array (grid) with dimensions (latitude, longitude, pressure). Latitude and longitude coordinates are sorted in ascending order.
    5. Handles missing files or empty data by returning None, which typically halts the simulation. NaN values in data are logged and filled with 0.
    6. The 3D grid is then flattened into a 1D array (row-major order) for compatibility with the C++ interpolator.
  • File Index Calculation (in HybridParticleTracker.load_velocity_data):
    hourrelative_to_csv_start = absolute_sim_hour - csv_actual_start_hour
    csv_file_index0based = floor(hourrelative_to_csv_start / data_interval_hours + 1e-9)
    csv_file_hour_index = csv_file_index0based + 1 (1-based index for filenames)
    Where absolute_sim_hour is the simulation time for which data is needed, and csv_actual_start_hour is the simulation_start_hour from the config for CSV mode.

4.2. API Data (APIDataHandler)

When data_source is "API", the APIDataHandler class is used.

  • CDS API Interaction: Uses the cdsapi Python client to request and download data (e.g., ERA5 reanalysis on pressure levels).
  • Data Download and Caching:
    • Downloads data in daily NetCDF files to a local directory (api_data_dir) to avoid repeated downloads.
    • Checks for existing files before attempting a new download for a given day.
    • Variables requested typically include u-component, v-component of wind, vertical velocity (omega), specific humidity, and temperature.
  • NetCDF Processing:
    • Uses xarray to open and process the downloaded NetCDF files.
    • Selects data for the specific target_datetime_utc (hour).
    • Handles different possible time coordinate names in NetCDF files (e.g., 'time', 'valid_time').
  • Coordinate System Handling:
    • Ensures latitude coordinates are sorted in ascending order (ERA5 data often has descending latitudes).
    • Transposes data arrays to a consistent order (latitude, longitude, pressure_level) before flattening. This ensures compatibility with the interpolators.
    • Pressure levels are taken from the configuration, assuming they match the levels in the downloaded NetCDF file.
  • Output: Returns tuples containing coordinate arrays (lats, lons, pressures) and the flattened data values for u, v, w, q (specific humidity), and t (temperature). Missing q or t variables are handled gracefully.

4.3. NetCDF Data (NCDataLoader)

When data_source is "NC" or "NETCDF", the NCDataLoader class is used. This enables direct simulation on multi-variable NetCDF datasets (such as combined HRRR/ERA5 files).

  • File Discovery: Scans the directory specified in nc_data_dir. It matches file naming conventions (defaulting to combined_YYYYMMDD_HH.nc) using regular expressions to construct a chronological map of datasets.
  • Automatic Metadata Extraction: Reads the first discovered NetCDF file to parse latitude, longitude, and pressure level coordinates, automatically injecting these coordinates into the simulation configuration.
  • Data Alignment: Checks dimension names ('latitude' vs 'lat', 'longitude' vs 'lon', 'level' vs 'pressure') and automatically transposes arrays to a standard (latitude, longitude, pressure) order.
  • Output formatting: Replaces missing NaN values with zero and flattens arrays into a row-major 1D structure for C++ bindings. Dynamic scalars (such as q, t, clwc, etc.) are extracted alongside core velocities if present in the NetCDF.

5. Particle Initialization

Particles are initialized on a regular grid in latitude, longitude, and pressure space. This is handled by HybridParticleTracker.initialize_particles, which can delegate to a C++ implementation or use a Python fallback.

  • Input Parameters: Latitude range, longitude range, initialization pressure levels, and desired approximate physical spacing (spacing_km).
  • Latitude Spacing (Δlat in degrees):
    deg_per_km_lat ≈ 1 / 111.0 (approx. km per degree latitude)
    Δlat = spacing_km * deg_per_km_lat
    This results in a roughly constant physical spacing in the latitudinal direction.
  • Longitude Spacing (Δlon in degrees):
    mid_lat_rad = radians((lat_start + lat_end) / 2)
    deg_per_km_lon_at_mid_lat ≈ 1 / (111.0 * cos(mid_lat_rad))
    Δlon = spacing_km * deg_per_km_lon_at_mid_lat
    This calculates a fixed degree spacing for longitude based on the cosine of the mid-latitude of the *entire initialization domain*.
  • Particle Placement: np.meshgrid (or equivalent logic) is used to create a grid of (lat, lon, pressure) points. Each point becomes an initial particle position.
  • Near-Pole Density: Because a single Δlon (in degrees) is used across all latitudes within the initialization domain, particles will be physically closer together (in kilometers) near the poles of the domain compared to its equator. This is an inherent characteristic of using a fixed degree spacing for longitude on a sphere.

6. Core Simulation Loop (HybridParticleTracker.run_simulation)

The main simulation loop orchestrates the particle tracking process over time.

  1. Initialization/Resumption:
    • Attempts to load a checkpoint if resume=True. If successful, particle states and the last completed simulation step are restored.
    • If no checkpoint is found or resumption is disabled, new particles are initialized. The initial state is saved and plotted.
  2. Time Management:
    • The loop iterates from a loop_start_step to a loop_end_step.
    • loop_end_step is determined by initial_absolute_step_offset + (total_duration_hours / simulation_step_hours).
    • initial_absolute_step_offset accounts for any simulation_start_hour offset.
  3. Initial Data Load: Loads velocity data for the current (current_data_hour) and next (next_data_hour) data intervals required for the first simulation step. Interpolators (interp_curr, interp_next) are created.
  4. Per Timestep:
    1. Data Interval Update (if needed): If the simulation time crosses into a new data interval (e.g., every data_interval_hours), the velocity data is cycled:
      • interp_curr becomes the previous interp_next.
      • New data is loaded for the *new* next_data_hour, and interp_next is updated.
      • The simulation stops if required data cannot be loaded.
      • If the simulation reaches the end of its configured duration and no more "next" data is needed, interp_curr is used for interp_next.
    2. Temporal Interpolation Factor (α): Calculated to determine the particle's position in time relative to the current_data_hour and next_data_hour.
      time_into_current_data_interval = current_sim_hours_elapsed - current_data_hour
      α = clip(time_into_current_data_interval / data_interval_hours, 0.0, 1.0)
    3. Particle Update: Calls update_particles (which may use the C++ engine or Python fallback) to advect particles using the RK4 method.
    4. Scalar Transport (q, t): If specific humidity (q) and temperature (t) data are available (primarily in API mode), their values at particle locations are interpolated using a similar temporal factor α_for_scalars.
    5. Output: If the current simulation time meets the output_interval_hours, particle positions (and q/t values if available) are saved to CSV or NetCDF, and a plot is generated.
    6. Checkpointing: If the current simulation step meets the checkpoint_interval_hours, the current particle state and simulation step are saved.
  5. Final Save: After the loop finishes, the final particle state is saved and plotted. A final checkpoint is also created.

7. Velocity Interpolation

To determine the velocity at a particle's exact location and time, spatial and temporal interpolation are performed.

7.1. Spatial Interpolation (Trilinear)

Velocity components (u, v, w) are typically available on a 3D regular grid (latitude, longitude, pressure). Trilinear interpolation is used to estimate the velocity at an arbitrary point (particle location) within a grid cell. This is implemented in both C++ (RegularGrid3DInterpolator) and Python (using scipy.interpolate.RegularGridInterpolator).

The formula for trilinear interpolation involves linearly interpolating along one axis (e.g., x), then using those results to interpolate along the second axis (e.g., y), and finally using those results to interpolate along the third axis (e.g., z). It can be expressed as a weighted average of the values at the 8 corners of the grid cell enclosing the point.

The C++ and Scipy interpolators require input coordinate arrays (latitude, longitude, pressure) to be sorted in ascending order. They handle points outside the grid bounds by using a specified fill_value (typically 0.0 for velocities, or NaN for scalars like q, t).

7.2. Temporal Interpolation

Since particle positions are updated at time steps (dt_seconds) that may fall between the times for which full velocity fields are available (data_interval_hours), linear temporal interpolation is used.

If V_curr is the velocity field at current_data_hour and V_next is the field at next_data_hour, the velocity V at an intermediate time (represented by the factor α) is:

V(t) = (1 - α) * V_curr + α * V_next

Where α is calculated as described in the simulation loop section. This is applied independently to u, v, and w components after they have been spatially interpolated.

8. Particle Advection (Runge-Kutta 4th Order)

The particle's new position is calculated by integrating its velocity over the simulation time step (dt_seconds). The Runge-Kutta 4th order (RK4) method is employed for its balance of accuracy and computational cost. This is implemented in serial (rk4_integrator.cpp) and parallel (rk4_integrator_parallel.cpp) C++ structures, with a Python fallback in particle_tracker.py.

OpenMP Multi-threading: When execution_mode is set to "parallel", HPT schedules the advection of particle batches concurrently using OpenMP threads. Thread count is controlled dynamically by the OMP_NUM_THREADS environment variable, enabling optimal performance scalability on multi-core CPU architectures.

Given a particle's current position Pn = (latn, lonn, pressuren) at time tn, its new position Pn+1 at tn + dt is found by:

k1 = dt ⋅ f(tn, Pn, αn)
k2 = dt ⋅ f(tn + dt/2, Pn + k1/2, αn+dt/2)
k3 = dt ⋅ f(tn + dt/2, Pn + k2/2, αn+dt/2)
k4 = dt ⋅ f(tn + dt, Pn + k3, αn+dt)
Pn+1 = Pn + (k1 + 2⋅k2 + 2⋅k3 + k4) / 6
Where:
  • dt is dt_seconds.
  • f(t, P, α) is the function that returns the velocity derivatives (dlat/dt, dlon/dt, dp/dt) at position P and time corresponding to temporal interpolation factor α.
  • α_n, α_{n+dt/2}, α_{n+dt} are the temporal interpolation factors calculated for the respective sub-steps of RK4. For example:
    αsubstep = initial_alpha_for_step + time_fraction_into_dt ⋅ (dt_seconds / (data_interval_hours ⋅ 3600.0))
    (time_fraction_into_dt is 0.0 for k1, 0.5 for k2/k3, 1.0 for k4).

8.1. Velocity Derivatives (get_velocity / get_velocity_derivatives)

The function f involves:

  1. Spatially and temporally interpolating u (m/s), v (m/s), and w (Pa/s) at the given particle position and sub-step time (using the sub-step α).
  2. Converting these meteorological velocities into coordinate derivatives:
dlat/dt (deg/s) = (v / R_earth) * (180 / π)
dlon/dt (deg/s) = (u / (R_earth * max(cos(lat_rad), MIN_COS_FACTOR))) * (180 / π)
dp/dt (hPa/s) = w_Pa_s / 100.0
Where:
  • R_earth is the Earth's radius (approx. 6371000 m).
  • lat_rad is latitude in radians.
  • MIN_COS_FACTOR (e.g., cos(85 degrees)) is used to prevent division by zero or excessively large dlon/dt near the poles (Polar Singularity Handling). If R_earth * max(cos(lat_rad), MIN_COS_FACTOR) is below a small threshold (e.g., 1e-6 in C++), dlon/dt is set to 0.

9. Boundary Conditions (Global Simulations)

For simulations on a global domain, specific boundary conditions are applied after each RK4 step to ensure particles remain within physical limits:

  • Latitude Clamping: The new latitude is clamped to the range [-90, 90] degrees.
    new_lat = clamp(new_lat, -90.0, 90.0)
  • Longitude Wrapping: The new longitude is wrapped to a standard range, typically [-180, 180) degrees.
    new_lon = new_lon - floor((new_lon + 180.0) / 360.0) * 360.0
  • Pressure Clamping: The new pressure is clamped to the minimum and maximum pressure levels of the input data grid.
    new_pressure = clamp(new_pressure, pressure_min_data, pressure_max_data)

10. Scalar Transport (Specific Humidity 'q' and Temperature 't')

If specific humidity (q) and temperature (t) data are available (primarily in API mode), their values at the new particle positions are calculated for output.

  • Data for q and t are loaded similarly to u, v, w components.
  • Scipy RegularGridInterpolator objects are created for q and t.
  • At each output step, after particles have been advected, the q and t values are interpolated at the final particle positions (lat, lon, pressure).
  • Both spatial (trilinear) and temporal interpolation are applied:
    S_particle = (1 - α_scalars) * S_curr_interpolated_at_particle + α_scalars * S_next_interpolated_at_particle
    Where S is the scalar (q or t), and α_scalars is the temporal interpolation factor corresponding to the particle's time at the end of the advection step, relative to the current_data_hour and next_data_hour.
  • The fill value for q and t interpolators is typically np.nan to distinguish missing scalar data from a value of zero.

11. Thermodynamic Tracking

The HPT framework allows tracking thermodynamic indicators along the trajectories of parcels to identify physical heating/cooling mechanisms.

  • Method 0: Simple Subtraction (SIMPLE_SUBTRACTION)
    Tracks raw temperature changes between time steps:
    ΔT = T(t) - T(t0)
  • Method 1: Potential Temperature & Dry Static Energy (POTENTIAL_TEMPERATURE)
    Factors out adiabatic expansion/compression along the trajectory:
    • Potential Temperature ($\theta$):
      θ = T ⋅ (P0 / P)κ
      where $P_0 = 1000$ hPa and $\kappa \approx 0.286$ ($R/C_p$).
    • Dry Static Energy (DSE):
      DSE = Cp ⋅ T + g ⋅ z
      where $C_p = 1004 \text{ J kg}^{-1}\text{K}^{-1}$, $g = 9.81 \text{ m s}^{-2}$, and $z$ is geopotential height.
    The tracker computes changes $\Delta\theta$ and $\Delta DSE$ to isolate non-adiabatic diabatic cooling/heating processes.
  • Method 2: Full Anomaly Decomposition (FULL_DECOMPOSITION)
    Implements the Papritz & Röthlisberger method to decompose temperature anomalies ($T'$) into four physical drivers integrated over the trajectory using numerical trapezoidal integration:
    T'(x,t) - T'(x0,t0) = Seasonality + Advection + Adiabatic + Diabatic
    Where:
    • Seasonality: $-\int \frac{\partial \overline{T}}{\partial t} d\tau$
    • Advective: $-\int \mathbf{v} \cdot \nabla_h \overline{T} d\tau$
    • Adiabatic: $\int \left[\frac{\kappa \overline{T}}{p} - \frac{\partial \overline{T}}{\partial p}\right] \omega d\tau$
    • Diabatic: $\int \left(\frac{p}{p_0}\right)^\kappa \frac{D\theta}{Dt} d\tau$
    This method requires pre-processed climatology background data ($\overline{T}$ and its spatial/temporal gradients) provided via the thermo_bg_file configuration.

12. Output (HybridParticleTracker.save_particles)

Particle data is saved at specified output_interval_hours.

  • CSV Format:
    • A CSV file is created for each output time.
    • Columns typically include: 'id', 'latitude', 'longitude', 'pressure', and optionally 'specific_humidity', 'temperature'.
    • When thermodynamic modes are active, columns also include `delta_t`, `delta_theta`, `delta_dse`, or the four decomposed drivers (seasonality, advection, adiabatic, diabatic terms).
  • NetCDF Format:
    • An Xarray Dataset is created with particle data.
    • Coordinates: 'particle_id' and optionally 'time'.
    • Data Variables: 'latitude', 'longitude', 'pressure', 'specific_humidity', 'temperature', and thermodynamic tracking terms (e.g. `delta_theta`, `delta_dse`, or seasonality, advection, adiabatic, and diabatic anomaly drivers), with appropriate units and long names as attributes.
    • _FillValue (typically NaN for floats) and dtype are specified in the encoding for robust NetCDF writing.
    • Global attributes like 'creation_date' and 'source_script' are included.
    • Saved using ds.to_netcdf(filename, engine="netcdf4", encoding=...).

13. Visualization (ParticleVisualizer)

The ParticleVisualizer class uses Matplotlib and Cartopy to create geographical plots.

  • Particle Positions (plot_particles):
    • Displays particles as scatter points on a map for a given time.
    • Map features like coastlines and gridlines are added using Cartopy.
    • Plot extent can be configured via plot_lat_range and plot_lon_range in the main configuration.
  • Particle Trajectories (plot_particle_trajectories):
    • If trajectory data is collected, this method plots lines representing the paths of selected particles. (Note: Trajectory collection logic is not explicitly detailed in the provided particle_tracker.py but this method exists in visualization.py).
  • Pressure Distribution (plot_pressure_distribution):
    • Generates a histogram showing the distribution of particles across different pressure levels.

14. C++ Engine (particle_engine_cpp)

The C++ engine is designed for performance-critical parts of the simulation.

  • Pybind11: Used to create Python bindings for the C++ classes, allowing them to be called directly from Python.
  • ParticleEngine (C++ class):
    • Main interface exposed to Python.
    • Contains methods like initialize_particles, create_interpolator, and update_particles (which takes a batch of particles and thermodynamic options).
  • RegularGrid3DInterpolator (C++ class):
    • Stores the 3D gridded data (e.g., u, v, w) and its coordinate axes.
    • Implements trilinear interpolation (interpolate(lat, lon, pressure) method).
    • Handles boundary checks and fill values. Coordinates are internally normalized for interpolation.
  • RK4Integrator (C++ class):
    • Implements the RK4 algorithm (integrate_particle method for serial particle advection).
    • Contains polar singularity handling and global boundary clamping/wrapping logic.
  • RK4IntegratorParallel (C++ class):
    • Implements OpenMP multi-threaded RK4 advection (integrate_batch method) to process large batches of particles concurrently across available CPU threads.
  • ThermoState (C++ structure):
    • Implements the thermodynamic integration algorithms (Simple, Potential Temp / DSE, and the 4-integral Papritz & Röthlisberger decomposition via numerical trapezoidal integration) calculated along each parcel trajectory step.

15. Build Process (build.py / setup.py)

The C++ components are compiled into a Python extension module using setuptools and pybind11.

  • setup.py defines a Pybind11Extension named particle_engine_cpp, listing source files (including parallel integration and thermodynamic module files) and configuring compile-time flags for OpenMP (e.g., /openmp on Windows, -fopenmp on Linux).
  • Unified Build Script (build.py): Cleans old build directories, uninstalls any conflicting versions, installs dependencies from requirements.txt, compiles/installs the package in editable mode (pip install -e .), and runs a comprehensive load test validation on both C++ and Python elements.

16. Testing and Consistency (test_simulation_consistency.py)

A dedicated test script, test_simulation_consistency.py, is provided to compare the results of the C++ RK4 implementation against a pure Python/Scipy RK4 implementation.

  • It initializes a small number of particles and loads a few time steps of data.
  • It creates both C++ interpolators (via the C++ engine) and Scipy RegularGridInterpolator objects using the same underlying data.
  • For each simulation step:
    • Particles are advected using the C++ engine.
    • Particles are advected using a Python RK4 implementation that mirrors the C++ logic but uses Scipy interpolators.
  • The positions and velocities (interpolated at the new positions) from both methods are compared.
  • Differences are printed, allowing verification that the C++ and Python advection schemes produce very similar results (within floating-point precision limits).
  • This is crucial for ensuring the correctness of the optimized C++ engine.

17. Conclusion

The Hybrid Parcel Tracker provides a robust and efficient framework for Lagrangian parcel simulations. By combining C++ for core computations and Python for high-level control and data management, it aims to offer both performance and flexibility. The system includes detailed data handling for CSV and API sources, a well-defined parcel advection scheme (RK4) with appropriate boundary conditions, and visualization capabilities.
